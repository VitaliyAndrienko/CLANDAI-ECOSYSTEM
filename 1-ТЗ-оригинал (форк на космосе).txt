# P2F Network — Техническое задание: Шард 0 (Genesis Shard) и протокол автоматического развёртывания шардов

**Статус:** архитектурный проект для технического ревью. Не является обещанием достижимости заявленной производительности. Не готов к mainnet без прототипа, нагрузочных испытаний и независимого аудита.

**Цель документа:** описать развёртывание первого блокчейна (Шард 0) и заложить в систему механизм автоматического создания и подключения дополнительных шардов (Spawn Protocol) для горизонтального масштабирования до 1 000 000 TPS суммарно.

---

## 0. Термины и нормативные слова

- **ДОЛЖЕН / MUST** — обязательное требование.
- **НЕ ДОЛЖЕН / MUST NOT** — запрещённое поведение.
- **СЛЕДУЕТ / SHOULD** — рекомендуемое решение; отклонение требует обоснования.
- **МОЖЕТ / MAY** — допустимый вариант.
- **Шард 0 (Genesis Shard)** — первый блокчейн сети P2F, развёрнутый на Cosmos SDK.
- **Контрольная цепочка (Control Chain)** — специализированный шард, отвечающий за реестр шардов, чекпоинты и кросс-шардовую маршрутизацию.
- **Spawn Protocol** — протокол автоматического создания, регистрации и подключения новых шардов.
- **Оператор** — человек/организация, управляющая VPS через ограниченный пульт.
- **Валидатор** — узел, голосующий за блоки в шарде.
- **Каноническое состояние** — состояние, вычисляемое по правилам протокола; определяет балансы и права.

---

## 1. Цели и не-цели

### 1.1 Цели

1. Развернуть **Шард 0** — работающий блокчейн на Cosmos SDK с CometBFT.
2. Обеспечить **10 000 TPS** на одном шарде.
3. Заложить в архитектуру **Spawn Protocol** для автоматического создания дополнительных шардов.
4. Реализовать **контрольную цепочку** для координации шардов.
5. Обеспечить **кросс-шардовую коммуникацию** через IBC.
6. Реализовать **защиту от махинаций валидаторов** через slashing, evidence, BFT-гарантии.
7. Обеспечить **data availability** для всех шардов.
8. Реализовать **governance** для управления протоколом.
9. Обеспечить **VPS-only** валидаторов с one-click deploy.
10. Масштабироваться до **100 шардов = 1 000 000 TPS** суммарно.

### 1.2 Не-цели

- Обещание 1 млн TPS до воспроизводимого бенчмарка.
- Собственный консенсус с нуля.
- Полная анонимность от валидаторов.
- Мгновенная атомарность кросс-шардовых операций.
- Автоматический spawn без PoP, VRF, Oracle, Attestation (MVP — whitelist).
- Исполнение произвольного native-кода Web2 без sandbox.

### 4.2 MVP-Spawn (Phase 2)

**Правила:**
- Только whitelist операторов (10–20).
- Ручное одобрение DAO (66%).
- Лимит 3 VPS на оператора.
- Cooldown 7 дней.
- Депозит 1000 P2F.
- Slashing при нарушении.
- Прозрачность всех событий.

### 4.3 Полный Spawn Protocol (Phase 6+)

**Правила:**
- Permissionless участие.
- PoP обязателен (минимум 2 провайдера).
- VRF-выбор среди заявок.
- Депозит 100 P2F.

- Oracle-верификация.
- Лимиты по репутации.
- KYC для крупных операторов.

### 4.4 VRF-выбор оператора

```
score = vrf_ticket / (reputation_factor * region_factor * asn_factor * vps_penalty)

reputation_factor = 1 + reputation / 1000
region_factor = 1 + region_bonus
asn_factor = 1 + asn_bonus
vps_penalty = 1 + vps_count / max_vps
```

Выбирается оператор с **наибольшим** score.

### 4.5 Лимиты и защита от Sybil

```
max_vps = BASE_MAX * reputation_factor * pop_factor * kyc_factor

BASE_MAX = 1
reputation_factor = 1 + reputation / 1000
pop_factor = 1 + (pop_providers - 2) * 0.5
kyc_factor = 1 + (kyc_verified ? 2 : 0)
```

| Статус | max_vps |
|---|---|
| Новый, 2 PoP | 1 |
| Проверенный, 4 PoP | 4 |
| Проверенный, 4 PoP + KYC | 12 |
| Топ, 6 PoP + KYC | 20 |

### 4.6 Cooldown между spawn

```
cooldown = BASE_COOLDOWN * (1 + vps_count) / reputation_factor

BASE_COOLDOWN = 24 часа
reputation_factor = 1 + reputation / 1000
```

### 4.7 Награды и депозиты

```
reward = base_reward * region_factor * urgency_factor * reputation_factor

base_reward = 50 P2F
region_factor = 1.0 - 2.0
urgency_factor = 1.0 - 3.0
reputation_factor = 1.0 - 2.0
```

**Slashing:**
| Нарушение | Штраф |
|---|---|
| Attestation не прошла | 10% депозита |
| Heartbeat отсутствует 30 мин | 5% депозита |
| Heartbeat отсутствует 2 часа | 50% депозита |
| Двойная подпись | 100% депозита |
| Вредоносный образ | 100% депозита |
| Сговор | 100% депозита + бан |

## 5. Защита от махинаций валидаторов

### 5.1 Экономический уровень: Slashing

**x/slashing** — модуль Cosmos SDK, который наказывает валидаторов за доказанное вредоносное поведение.

| Нарушение | Наказание |
|---|---|
| Double-signing (двойная подпись) | 100% стейка + tombstone (пожизненный бан) |
| Downtime (простой) | Jailing (арест) + частичный slashing |

**Tombstone cap:** валидатор может быть слэшнут за двойную подпись только один раз за инцидент. Это предотвращает катастрофические последствия от случайных ошибок HSM.

### 5.2 Доказательный уровень: x/evidence

**x/evidence** — модуль, который позволяет любому отправить доказательство нарушения в блокчейн.

```rust
struct Evidence {
    type: DoubleVoting | LightClientAttack | ...
    validator: Address,
    height: u64,
    time: u64,
    proof: bytes,
}
```

**Handler:** проверяет доказательство и инициирует slashing, jailing, tombstoning.

### 5.3 Математический уровень: BFT-гарантии

CometBFT гарантирует безопасность (отсутствие форков), пока **менее 1/3** от общего объёма голосующей мощности действуют византийски.

**Порог безопасности:** даже если 33% валидаторов сговорились, они не смогут заставить сеть принять неверный блок. Им нужно контролировать более 2/3 сети.

### 5.4 Защита от фронтраннинга: Vote Extensions

ABCI 2.0引入 **Vote Extensions** — механизм, который позволяет валидаторам обмениваться информацией о мемпуле до формирования блока. Это позволяет создать более справедливый порядок транзакций и бороться с MEV-атаками.

### 5.5 Slash Throttling

Механизм **slash throttling** гарантирует, что за один раз может быть наказана только определённая доля валидаторов. Это предотвращает сценарий, когда одна вредоносная цепочка может «убить» безопасность главной сети.

### 5.6 Защита от Sybil

| Уровень | Механизм |
|---|---|
| PoP | Worldcoin, Gitcoin Passport, BrightID |
| Депозит | 100–1000 P2F за узел |
| Лимит | max_vps по репутации и PoP |
| VRF | Случайный выбор комитета |
| Ротация | Смена валидаторов каждую эпоху |
| Прозрачность | Все spawn-события публичны |

## 6. Кросс-шардовая коммуникация (IBC)

### 6.1 IBC v2

IBC v2 обеспечивает прямую связь между Cosmos-цепочками и EVM-совместимыми сетями.

**Компоненты:**
- Light clients — проверка состояния друг друга.
- Relayers — передача сообщений.
- IBC Core — маршрутизация.

### 6.2 Кросс-шардовый протокол

```protobuf
message CrossShardMessage {
    bytes message_id = 1;    // hash(shard_from, shard_to, nonce, payload)
    uint32 shard_from = 2;
    uint32 shard_to = 3;
    bytes sender = 4;
    bytes recipient = 5;
    bytes asset_id = 6;
    uint256 amount = 7;
    uint64 nonce = 8;
    bytes proof = 9;          // Merkle proof финализации
    uint64 valid_until_height = 10;
}
```

**Правила:**
- Блокировка/списание на исходном шарде.
- Proof финализации исходной операции.
- Однократное применение на целевом (`processed_messages` set).
- Тайм-аут → возврат.
- Защита от двойного расходования.
- Финалити — после подтверждения от целевого.

### 6.3 API IBC


## 8. Governance

### 8.1 Модель

- **Предложение:** любой оператор с ≥ N узлов или ≥ X репутации.
- **Обсуждение:** 7 дней.
- **Голосование:** 7 дней.
- **Timelock:** 48 часов.
- **Активация:** на заданной высоте блока.

### 8.2 Voting Power

```
power = reputation^0.5 * uptime_factor * log(1 + service_score)
```

- Логарифм — чтобы крупные не доминировали.
- Квадратный корень — анти-плаутократия.

### 8.3 Quorum

- 33% от общего voting power.
- 50%+1 от проголосовавших.
- Для критических изменений — 66%.

### 8.4 Break-glass

- Multi-sig из 7 независимых аудиторов.
- 5 из 7 подписей.
- Только для остановки сети при критической уязвимости.
- Не может переводить средства.
- Публичный журнал.

## 12. Тестирование и приёмка

### 12.1 MVP

- 4 локальных валидатора, одинаковый app/state root.
- Тесты: перевод, nonce, комиссии, недостаток средств, невалидная подпись, повтор, истёкшая tx.
- Два узла с одинаковой конфигурацией → одинаковый результат.
- Перезапуск восстанавливает состояние, проходит проверку корня.
- PostgreSQL удаляется и пересоздаётся без потери канонического состояния.
- Подписанный релиз проходит проверку.
- Нагрузочные тесты публикуют valid finalized TPS.
- Отказ одного узла не приводит к двойному исполнению.

### 12.2 Безопасность перед тестнетом

- Fuzzing parser/serialization/RPC/decoder.
- Property-based tests для balances, supply, nonce, AMM.
- Differential test между сборками/платформами.
- Fault injection: задержки, дубли, перестановка, потеря, повреждение.
- Тест конфликтующих tx и повторного исполнения.
- Threat-model review.
- Независимый аудит консенсуса, ключей, обновлений, экономики допуска.
- Проверка восстановления после state corruption и недоступности DA.

### 12.3 Критерии 1 млн TPS

- 1 000 000 валидных финализированных tx/с по всем шардам на опубликованном профиле.
- ≥ 60 минут устойчивой нагрузки после прогрева.
- Опубликованные hardware/network specs.
- Проверка восстановления после отказа части узлов.
- p50/p95/p99 latency, доля ошибок.
- Учёт DA/storage/replication.
- Независимое воспроизведение.
- Отдельный отчёт по кросс-шарду и тяжёлому исполнению.

# P2F Network — Система геймификации на поинтах v0.1

**Статус:** архитектурная спецификация. Не входит в MVP Phase 1. Входит в Phase 2.

**Назначение:** описать систему поинтов для мотивации участников сети без привязки к токену. Поинты — это учёт полезного вклада. Конвертация в токены будет определена позже через governance.

**Ключевой принцип:** поинты нельзя купить. Только заработать полезной работой.

---

## 0. Термины

- **Поинт (P2F Point, PFP)** — единица учёта полезного вклада.
- **Уровень** — статус участника, зависящий от поинтов и других факторов.
- **Эпоха** — период пересчёта (24 часа).
- **Сезон** — период сброса части поинтов (90 дней).
- **Вклад** — измеримое полезное действие.
- **Множитель** — коэффициент, увеличивающий начисление.
- **Анти-абьюз** — механизмы против накрутки.

---

## 1. Философия

### 1.1 Что такое поинты

Поинты — это **не токен**. Это учёт вклада. Они:

- начисляются за полезную работу;
- не передаются между участниками;
- не покупаются;
- не дают voting power напрямую;
- конвертируются в токены только через governance.

### 1.2 Почему поинты, а не токены сразу

- Нет привязки к рыночной цене.
- Нет спекуляций на старте.
- Можно калибровать формулу без финансовых последствий.
- Governance решает конвертацию позже.

### 1.3 Принципы

1. **Поинты нельзя купить.** Только заработать.
2. **Поинты нельзя передать.** Они привязаны к адресу.
3. **Поинты не дают voting power.** Governance — отдельно.
4. **Формула публична.** Каждый может проверить.
5. **Анти-абьюз обязателен.** Накрутка наказывается.
6. **Сезонность.** Часть поинтов сбрасывается каждые 90 дней.
7. **Прозрачность.** Все начисления публичны.

### 2.1 Роли

| Роль | Что делает | Поинты за |
|---|---|---|
| Loader | Принимает tx, антиспам | Принятые tx |
| Pricer | Симуляция AMM, проверка | Симуляции |

### 2.2 Вклад

**Измеримый вклад** — это действие, которое:

- проверяемо;
- полезно сети;
- не может быть накручено без последствий.

**Примеры:**
- Принял 100 tx за эпоху → +100 PFP.
- Держал узел онлайн 24 часа → +50 PFP.
- Проголосовал в governance → +10 PFP.
- Пригласил активного участника → +20 PFP.

## 3. Формула начисления

### 3.1 Базовая формула

```
points_earned = base_points 
              * quality_factor 
              * uptime_factor 
              * reputation_factor 
              * streak_factor
              * season_factor
```

### 3.2 Компоненты

#### base_points
Фиксированное количество за действие.

| Действие | base_points |
|---|---|
| Принятая tx (loader) | 1 |
| Симуляция (pricer) | 2 |
| Репликация блока (replica) | 5 |
| Хранение данных (DA) | 3 |
| Запрос API (indexer) | 0.1 |
| Исполнение (app executor) | 10 |
| Подписанный блок (validator) | 100 |
| Голос в governance | 10 |
| Час uptime | 2 |
| Активный реферал | 20 |

#### quality_factor
Зависит от качества работы.

```
quality_factor = 1.0 + (quality_score - 0.5) * 0.5

quality_score = [0, 1]
```

- Если quality = 0.5 → factor = 1.0.
- Если quality = 1.0 → factor = 1.25.
- Если quality = 0.0 → factor = 0.75.

**Как считается quality:**
- Для loader: доля принятых tx без ошибок.
- Для pricer: доля симуляций, совпавших с каноническим результатом.
- Для validator: доля подписанных блоков без пропусков.
- Для DA: доля доступных данных.

#### uptime_factor
Зависит от доступности.

```
uptime_factor = min(uptime / 0.99, 1.5)

uptime = доля времени онлайн за эпоху
```

- 99% → 1.0.
- 99.5% → 1.005.
- 100% → 1.01.
- Максимум 1.5 (при 148.5% — невозможно, значит кап).

**Реально:** uptime_factor = 1.0 при 99%, 1.01 при 100%.

#### reputation_factor
Зависит от репутации.

```
reputation_factor = 1.0 + reputation / 10000

reputation = [0, 10000]
```

- reputation = 0 → 1.0.
- reputation = 1000 → 1.1.
- reputation = 10000 → 2.0.

**Как растёт reputation:**
- +10 за эпоху без нарушений.
- +50 за закрытый спор в пользу участника.
- -100 за доказанное нарушение.
- -1000 за критическое нарушение.

#### streak_factor
Зависит от непрерывной работы.

```
streak_factor = 1.0 + min(streak_days, 30) * 0.01

streak_days = дней подряд без пропусков
```

- 1 день → 1.01.
- 10 дней → 1.10.
- 30 дней → 1.30.
- Максимум 1.30.

**Сброс:** пропуск дня → streak = 0.

#### season_factor
Зависит от сезона.

```
season_factor = 1.0 + season_bonus

season_bonus = [0, 0.5]
```

- Сезон 1 (первые 90 дней): +0.5.
- Сезон 2: +0.3.
- Сезон 3: +0.1.
- Сезон 4+: 0.

**Зачем:** стимулировать ранних участников.

### 3.3 Пример расчёта

**Loader принял 100 tx за эпоху:**
```
base_points = 100
quality_factor = 1.1  (quality = 0.7)
uptime_factor = 1.0   (99% uptime)
reputation_factor = 1.05  (reputation = 500)
streak_factor = 1.1   (10 дней подряд)
season_factor = 1.5   (сезон 1)

points = 100 * 1.1 * 1.0 * 1.05 * 1.1 * 1.5 = 190.575 PFP
```

**Validator подписал 100 блоков:**
```
base_points = 100 * 100 = 10000
quality_factor = 1.2   (quality = 0.9)
uptime_factor = 1.0
reputation_factor = 1.1
streak_factor = 1.3
season_factor = 1.5

points = 10000 * 1.2 * 1.0 * 1.1 * 1.3 * 1.5 = 25740 PFP
```

## 5. Специальные бонусы

### 5.1 Idle Bonus

**Зачем:** мотивировать операторов держать простаивающие шарды онлайн.

```
idle_bonus = IDLE_MAX * (1.0 - load / capacity)

IDLE_MAX = 0.5
load = текущая загрузка шарда (tx/сек)
capacity = максимальная пропускная способность
```

| Загрузка | idle_bonus |
|---|---|
| 0% | +50% |
| 25% | +37.5% |
| 50% | +25% |
| 75% | +12.5% |
| 100% | +0% |

**Применяется к:** всем поинтам, заработанным на этом шарде.

### 5.2 Routing Bonus

**Зачем:** мотивировать кросс-шардовую маршрутизацию.

```
routing_bonus = ROUTING_BASE * log(1 + routed_tx)

ROUTING_BASE = 0.05
routed_tx = маршрутизированные tx за эпоху
```

| routed_tx | routing_bonus |
|---|---|
| 0 | +0% |
| 10 | +12% |
| 100 | +23% |
| 1000 | +35% |
| 10000 | +46% |

**Применяется к:** поинтам шарда-маршрутизатора.

### 5.3 Referral Bonus

**Зачем:** мотивировать привлечение участников.

```
referral_bonus = REFERRAL_BASE * log(1 + active_referrals)

REFERRAL_BASE = 0.1
active_referrals = рефералы с > 1000 PFP
```

| active_referrals | referral_bonus |
|---|---|
| 0 | +0% |
| 1 | +7% |
| 10 | +24% |
| 100 | +46% |
| 1000 | +69% |

**Ограничения:**
- Только активные рефералы (> 1000 PFP).
- Не даёт voting power.
- Не даёт приоритет в консенсусе.
- Максимум +100%.

### 5.4 Long-term Bonus

**Зачем:** мотивировать долгосрочное участие.

```
long_term_bonus = min(months_active, 24) * 0.01

months_active = месяцев с первого заработанного PFP
```

| Месяцев | long_term_bonus |
|---|---|
| 1 | +1% |
| 6 | +6% |
| 12 | +12% |
| 24 | +24% |

**Максимум:** +24%.

### 5.5 Shard Pioneer Bonus

**Зачем:** мотивировать запуск новых шардов.

```
pioneer_bonus = 1.0 для первых 10 операторов нового шарда
              = 0.5 для следующих 20
              = 0.0 для остальных
```

**Применяется:** первые 30 дней существования шарда.

## 6. Сезонность

### 6.1 Сезоны

- Сезон = 90 дней.
- 4 сезона в году.
- Сезон 1 — с запуска сети.

### 6.2 Сброс поинтов

В конце сезона:

```
points_kept = points_earned * SEASON_KEEP
points_reset = points_earned * (1 - SEASON_KEEP)

SEASON_KEEP = 0.7
```

- 70% поинтов переносятся.
- 30% сбрасываются.

**Зачем:**
- Стимулировать постоянную работу.
- Не давать «застрять» на старых заслугах.
- Обновлять лидерборд.

### 6.3 Уровни не сбрасываются

Уровень участника не сбрасывается. Только поинты.

**Пример:**
- Участник набрал 100 000 PFP → Gold.
- В конце сезона 30 000 сброшено → 70 000 PFP.
- Уровень остаётся Gold.
- Для Diamond нужно 10 000 000 PFP.

## 7. Анти-абьюз

### 7.1 Основные атаки

| Атака | Как работает | Защита |
|---|---|---|
| Накрутка tx | Спам транзакциями | Quality factor, лимиты |
| Накрутка uptime | Fake heartbeat | Подпись, attestation |
| Накрутка рефералов | Фейковые аккаунты | PoP, активность > 1000 PFP |
| Накрутка симуляций | Фейковые запросы | Quality factor, проверка |
| Накрутка голосов | Много аккаунтов | PoP, репутация |
| Sybil | Много узлов | PoP, депозит, лимиты |
| Сговор | Группа участников | Прозрачность, апелляция |

### 7.2 Quality Factor

**Для loader:**
```
quality = принятые_без_ошибок / всего_принятых
```

**Для pricer:**
```
quality = симуляций_совпало / всего_симуляций
```

**Для validator:**
```
quality = подписанных_блоков / всего_блоков
```

**Для DA:**
```
quality = доступных_данных / всего_данных
```

**Правила:**
- Quality < 0.5 → quality_factor = 0.75.
- Quality > 0.9 → quality_factor = 1.2.
- Quality = 0 → points = 0.

### 7.3 Лимиты

| Действие | Лимит в эпоху |
|---|---|
| Принятые tx | 10 000 |
| Симуляции | 5 000 |
| Репликации | 1 000 |
| Запросы API | 100 000 |
| Исполнения | 500 |
| Подписанные блоки | 100 |
| Голоса | 10 |
| Часы uptime | 24 |

**Превышение лимита:** поинты не начисляются.

### 7.4 Аномалии

Система отслеживает:

- резкий рост поинтов;
- аномально высокий quality;
- множественные рефералы за короткое время;
- одинаковые паттерны у разных участников;
- коррелированные действия.

**При обнаружении:** флаг для ручного review.

### 7.5 Санкции

| Нарушение | Санкция |
|---|---|
| Накрутка tx | Сброс поинтов за эпоху |
| Fake heartbeat | Сброс поинтов за 7 дней |
| Фейковые рефералы | Сброс реферальных поинтов |
| Sybil | Бан, сброс всех поинтов |
| Сговор | Бан, сброс всех поинтов |

**Апелляция:** через DAO. 7 дней.

### 7.6 Прозрачность

- Все начисления публичны.
- Все формулы публичны.
- Все санкции публичны.
- Лидерборд публичен.
- API для проверки.

## 12. Governance

### 12.1 Что решает governance

- Формула начисления.
- Значения `base_points`.
- Значения `IDLE_MAX`, `ROUTING_BASE`, `REFERRAL_BASE`.
- Значения `SEASON_KEEP`.
- Требования уровней.
- Конвертация поинтов в токены (позже).

### 12.2 Как решает

- Предложение → обсуждение (7 дней) → голосование (7 дней) → timelock (48 ч).
- Quorum: 33% от voting power.
- Порог: 50%+1.
- Критические изменения: 66%.

### 12.3 Voting power

- Не поинты.
- Репутация × uptime × log(service).
- Отдельно от геймификации.

## 18. Ключевой принцип

**Поинты — это учёт полезного вклада, а не спекулятивный актив.**

- Нельзя купить.
- Нельзя передать.
- Нельзя накрутить без последствий.
- Не дают власти.
- Конвертируются в токены только через governance.

**Цель геймификации:**
- Мотивировать простаивающие шарды.
- Стимулировать рост сети.
- Поощрять долгосрочное участие.
- Награждать полезную работу.
- Не создавать pay-to-win.
- Не создавать плаутократию.

## 2. Три режима приложений

### 2.1 Режим A — Детерминированное исполнение

**Для кого:** DeFi, простые игры, логика с чёткими правилами.

**Как выглядит:**

```
Разработчик → пишет код → компилирует → загружает в шард
                                              │
                                              ▼
                                    ┌──────────────────┐
                                    │  WASM / EVM      │
                                    │  контракт        │
                                    └──────────────────┘
                                              │
                                              ▼
                              Валидаторы исполняют код
                              каждый независимо
                                              │
                                              ▼
                              Результат одинаков на всех
                                              │
                                              ▼
                              Состояние обновляется
```

**Технологии:**
- **CosmWasm** — для Rust-разработчиков.
- **Cosmos EVM** — для Solidity-разработчиков.
- **Wasmtime** — sandbox, детерминированный fuel.

**Что видит разработчик:**
- Знакомый стек: Rust или Solidity.
- Привычные инструменты: Hardhat, Foundry, MetaMask.
- Деплой как в Ethereum: одна транзакция.
- Полная проверяемость: каждый валидатор воспроизводит результат.

**Что видит пользователь:**
- Кошелёк B2C или B2B.
- Транзакции за 1–2 секунды.
- Комиссии в P2F.
- Полная история (если публичный режим).

### 2.2 Режим B — Anchored State

**Для кого:** реалтайм-игры, соцсети, тяжёлые вычисления.

**Как выглядит:**

```
Разработчик → держит свои серверы → пишет логику off-chain
                                              │
                                              ▼
                                    ┌──────────────────┐
                                    │  Внешний сервер  │
                                    │  (игра, соцсеть) │
                                    └──────────────────┘
                                              │
                                              ▼
                              Периодически отправляет
                              state root + checkpoint
                                              │
                                              ▼
                                    ┌──────────────────┐
                                    │  Шард P2F        │
                                    │  фиксирует       │
                                    │  обязательство   │
                                    └──────────────────┘
                                              │
                                              ▼
                              Данные доступны через DA
                              (Celestia / Avail)
```

**Что видит разработчик:**
- Свои серверы остаются.
- Логика не переписывается.
- Интеграция через SDK.
- Отправка чекпоинтов в P2F.

**Что видит пользователь:**
- Игра работает быстро (off-chain).
- Активы защищены (on-chain).
- Покупки и продажи через P2F.
- История транзакций в P2F.

**Ограничение:** хеш состояния доказывает неизменность, но не честность исполнения. Нужны fraud proofs или validity proofs для полной защиты.

### 2.3 Режим C — Гибрид

**Для кого:** большинство современных приложений.

**Как выглядит:**

```
┌─────────────────────────────────────────────────────────┐
│  Off-chain (быстро)                                     │
│  - UI, рендеринг                                        │
│  - Real-time симуляция                                  │
│  - Тяжёлые вычисления                                   │
│  - Соцграф                                              │
└─────────────────────────────────────────────────────────┘
                          │
                          │ события, чекпоинты
                          ▼
┌─────────────────────────────────────────────────────────┐
│  On-chain (безопасно)                                   │
│  - Владение активами                                    │
│  - Платежи                                              │
│  - Инвентарь                                            │
│  - Лимиты                                               │
│  - Финальные результаты                                 │
└─────────────────────────────────────────────────────────┘
```

**Что видит разработчик:**
- Гибридная архитектура.
- Критичные данные — on-chain.
- Быстрые данные — off-chain.
- SDK для интеграции.

**Что видит пользователь:**
- Быстрый UI.
- Безопасные активы.
- Прозрачные транзакции.
- Кошелёк B2C или B2B.

---

## 3. Что видит разработчик при загрузке приложения

### 3.1 Процесс

```
1. Регистрация
   └─ Разработчик создаёт аккаунт в P2F.

2. Выбор режима
   └─ AI-агент анализирует код.
   └─ Предлагает Mode A / B / C.
   └─ Разработчик подтверждает.

3. Загрузка кода
   └─ Mode A: компиляция в WASM / Solidity.
   └─ Mode B: SDK для чекпоинтов.
   └─ Mode C: гибридный SDK.

4. Проверка
   └─ AI-агент проверяет код.
   └─ Статический анализ.
   └─ Тесты в sandbox.
   └─ Ручной review (для критичных).

5. Деплой
   └─ Приложение регистрируется в Control Chain.
   └─ Получает app_id.
   └─ Создаётся B2B кошелёк.
   └─ Приложение готово.

6. Обновления
   └─ Новая версия → новый hash.
   └─ Старая версия не переписывается.
   └─ Пользователи видят changelog.
```

### 3.2 Что получает разработчик

- **app_id** — уникальный идентификатор.
- **B2B кошелёк** — для управления активами приложения.
- **SDK** — для интеграции.
- **Dashboard** — метрики, логи, пользователи.
- **API** — для внешних интеграций.
- **Документация** — туториалы, примеры.

---

## 4. Что видит пользователь

### 4.1 Кошельки

**B2C кошелёк:**
- Для обычных пользователей.
- Управление ключами через MPC.
- Session keys для приложений.
- Лимиты, whitelist.

**B2B кошелёк:**
- Для приложений.
- Ввод/вывод только по коду приложения.
- Policies, allowlist.
- Аудит всех операций.

Масштабирование шардов в P2F Network будет работать как автоматическая, самоподдерживающаяся система, которая реагирует на нагрузку в реальном времени. Это ключевой механизм для достижения целевых 1 000 000 TPS. В основе лежит мониторинг ключевых показателей (KPI), на основе которых протокол принимает решение о запуске нового шарда.

### ⚙️ Механика масштабирования: Триггеры и Процесс

Система не ждет ручного вмешательства. Масштабирование запускается автоматически при достижении пороговых значений KPI, которые отслеживаются в `Control Chain`.

**Ключевые KPI (Триггеры для масштабирования):**

*   **Утилизация блока (Block Utilization):** Основной показатель. Если средняя загрузка газового лимита в блоках шарда превышает **80%** в течение определенного периода (например, 1 минуты), это сигнал к расширению.
*   **Пропускная способность (TPS):** Если фактический TPS шарда приближается к его расчетному максимуму (например, **8 000 TPS** при лимите в 10 000), система готовится к запуску нового шарда.
*   **Задержка финализации (Finality Latency):** Если время до финализации блока стабильно превышает целевой показатель (например, **3 секунды**), это может указывать на необходимость перераспределения нагрузки.
*   **Плата за газ (Gas Fees):** Резкий рост средней комиссии может свидетельствовать о конкуренции за пространство в блоке, что также является триггером для расширения.

**Процесс запуска нового шарда (Spawn Protocol):**

1.  **Обнаружение:** `Control Chain` фиксирует устойчивое превышение пороговых значений KPI в одном из шардов.
2.  **Формирование запроса:** `Control Chain` создает `SpawnRequest` — публичный запрос на создание нового шарда с указанием требуемых ресурсов (CPU, RAM, регион).
3.  **Выбор оператора:** Операторы VPS подают заявки. Система выбирает оператора с помощью **VRF (Verifiable Random Function)** с учетом их репутации и текущей нагрузки, чтобы избежать централизации и гонки.
4.  **Развертывание:** Выбранный оператор разворачивает новый VPS и устанавливает на него стандартный Docker-образ P2F.
5.  **Регистрация:** Новый шард генерирует свои ключи и регистрируется в `Control Chain`, проходя проверку через **Google Cloud Attestation** для подтверждения целостности кода.
6.  **Интеграция:** Новый шард подключается к сети через **IBC (Inter-Blockchain Communication)**, становясь доступным для кросс-шардовых транзакций.

### 📊 Ключевые показатели эффективности (KPI)

Для управления сетью и оценки ее здоровья используется набор KPI. Они делятся на технические и экономические.

**Технические KPI:**

*   **TPS (Транзакций в секунду):** Основной показатель производительности. Цель — 10 000 TPS на шард и 1 000 000 TPS суммарно.
*   **Время финализации (Finality Time):** Целевое значение — **1–2 секунды** для мгновенного подтверждения транзакций.
*   **Задержка сети (Network Latency):** p99 задержка должна быть минимальной (например, <100 мс), чтобы обеспечить быстрый консенсус.
*   **Uptime:** Доступность каждого узла и шарда должна быть не менее **99%**. Это критически важно для надежности сети.
*   **Стоимость транзакции (Transaction Cost):** Средняя комиссия должна оставаться низкой и предсказуемой, чтобы привлекать пользователей.
*   **Эффективность параллельного исполнения (Block-STM):** Скорость обработки транзакций должна увеличиваться пропорционально количеству ядер CPU (целевой показатель — ускорение в **5-10 раз** на параллелизуемых нагрузках).

**Экономические KPI (для системы геймификации):**

*   **Средний PFP за эпоху:** Показывает активность и вклад участников. Например, для валидатора это может быть 10 000 PFP.
*   **Доля активных рефералов:** Процент рефералов, которые активно участвуют в сети (например, >50%).
*   **Средний Streak (дней подряд):** Показывает стабильность работы операторов (например, >7 дней).
*   **Коэффициент Slashing:** Доля участников, подвергшихся штрафам за нарушения (цель — <0.1%).

### 📈 Пример работы системы

Представим, что шард #1, на котором запущено популярное DeFi-приложение, начинает испытывать нагрузку.

1.  **Нагрузка растет:** TPS шарда #1 превышает **8 000**, утилизация блока — **85%**. KPI фиксируют это в течение 1 минуты.
2.  **Триггер срабатывает:** `Control Chain` автоматически создает `SpawnRequest` на новый шард.
3.  **Развертывание:** Оператор разворачивает новый VPS. Через несколько минут новый шард #5 регистрируется в сети.
4.  **Балансировка:** Часть новых транзакций и смарт-контрактов автоматически перенаправляется на шард #5 через IBC. Нагрузка на шард #1 снижается до комфортных 60%.
5.  **Обратное слияние (Downscaling):** Если нагрузка на всех шардах падает (например, в ночное время), и TPS на каком-либо шарде стабильно держится ниже **2 000** в течение 5 минут, система может инициировать процедуру слияния шардов для экономии ресурсов.

### 💎 Итог

Система масштабирования P2F — это **автоматический, самоподдерживающийся механизм**, который позволяет сети эластично расширяться и сжиматься в зависимости от нагрузки. В основе лежит мониторинг четких KPI (TPS, утилизация, задержка) и использование **Spawn Protocol** для быстрого и безопасного добавления новых вычислительных мощностей. Это обеспечивает сети способность достигать целевых 1 000 000 TPS, сохраняя при этом низкие комиссии и высокую скорость финализации.


## 🔴 Критические разделы

### 1. Токеномика

**Общий supply:** 1 000 000 000 P2F (1 млрд). Это стандарт для сетей с долгосрочным горизонтом.

**Распределение:**

| Категория | Доля | Vesting |
|---|---|---|
| Сообщество и награды | 40% | 10 лет, линейно |
| Команда | 15% | 4 года, cliff 1 год |
| Инвесторы | 15% | 3 года, cliff 1 год |
| Фонд развития | 15% | 10 лет |
| Резервный пул (slashing) | 10% | 10 лет |
| Публичное распределение | 5% | сразу |

**Инфляция:** 2% в год. Идёт на награды валидаторам и операторам. В Cosmos SDK это реализуется через модуль `x/mint`, где инфляция привязывается к проценту застейканных токенов (goal % bonded). Если застейкано больше цели — инфляция снижается до минимума; если меньше — растёт. Можно задать кастомную `MintFn` для специализированной логики.

**Сжигание:** 50% от базовой комиссии сжигается. 50% идёт в резервный пул.

**Связь PFP → P2F:** конвертация только через governance. Курс определяется после сбора данных о начислениях за первые 2–3 сезона. Возможные модели: фиксированный курс, динамический курс (от общего supply PFP), периодические дропы.

**Fee assets:** только P2F. Стейблы — через AMM, не напрямую.

**Treasury:** управляется governance. Расходы — через предложения с timelock 48 часов.

### 2. Безопасность шардов (межшардовое доверие)

**Модель:** IBC light clients + fraud proofs.

**Как работает:**
- Каждый шард запускает light client для каждого другого шарда.
- Light client проверяет блок-заголовки и консенсусные подписи.
- IBC обеспечивает криптографическую верификацию без централизованного моста.
- Validity predicate проверяет обновления состояния удалённой машины.

**Fraud proofs vs validity proofs:**
- **Validity proofs** дают криптографическую гарантию, но дороги в вычислении.
- **Fraud proofs** работают по optimistic модели: транзакция считается валидной, пока не доказано обратное в течение периода оспаривания.

**Рекомендация:** гибрид. Для мелких сумм — optimistic с периодом оспаривания 1 час. Для крупных (> X P2F) — validity proofs или увеличенный период.

**Механизм оспаривания:**
- Любой может подать fraud proof с Merkle-доказательством.
- Если proof верен — чекпоинт откатывается, валидаторы шарда slashing.
- Награда за fraud proof: 10% от slashed суммы.

**Модуль `x/evidence`** позволяет любому отправить доказательство нарушения, которое затем передаётся в основную цепь для slashing.

### 3. Emergency procedures

**Incident response plan:**

| Ситуация | Действие | Кто решает |
|---|---|---|
| Компрометация шарда (>1/3 сговор) | Остановка шарда, slashing, перевыбор комитета | Break-glass 5 из 7 |
| Остановка Control Chain | Emergency upgrade через `cosmovisor --upgrade-height` | Break-glass 5 из 7 |
| Потеря DA-данных | Приостановка операций шарда, восстановление из реплик | Автоматически + операторы |
| Критическая уязвимость консенсуса | Emergency upgrade, откат до последнего чекпоинта | Break-glass 5 из 7 |
| Атака на bridge | Заморозка IBC-канала, расследование | Break-glass 5 из 7 |
| Массовый slashing | Приостановка slashing, review | Governance |

**Emergency upgrade** — процедура, позволяющая обойти governance при критической необходимости. Используется `cosmovisor` с флагом `--upgrade-height`.

**`x/crisis`** — модуль, который останавливает блокчейн при нарушении инварианта. В v0.53+ депрекирован, но логика перенесена в другие модули.

**Роли:**
- **Break-glass (5 из 7):** только остановка/возобновление, не перевод средств.
- **Security contact:** обязателен для всех операторов.
- **dCERT group:** группа для экстренного реагирования, может быть распущена при сговоре.

### 4. Выбор комитета валидаторов для шардов

**Кто выбирает:** Control Chain через VRF.

**Размер комитета:** 
- Минимум: 10 валидаторов.
- Оптимум: 50 валидаторов.
- Максимум: 100 валидаторов.

**Как выбираются:**
- Операторы подают заявки на участие в шарде.
- VRF выбирает из подавших с учётом:
  - стейка (минимум 1000 P2F);
  - репутации;
  - текущей нагрузки (vps_count / max_vps);
  - региона/ASN (для распределения).

**Ротация:** каждую эпоху (24 часа). 20% комитета меняется.

**Если недостаточно желающих:**
- Шард работает с меньшим комитетом.
- Если < 10 — шард переходит в режим read-only.
- Control Chain создаёт SpawnRequest с повышенной наградой.

**VRF:** ECVRF на Ed25519. Доказано, что добавление ECVRF в процедуру консенсуса не вызывает критической деградации. Модуль ECVRF может быть интегрирован в Cosmos SDK и совместим с CosmWasm.

---

### 5. State migration между шардами

**Когда:** при перегрузке шарда (TPS > 80% capacity стабильно).

**Как:**
1. Создаётся snapshot состояния на высоте H.
2. Snapshot мигрируется асинхронно через MigrationStream.
3. Новый шард инициализируется с мигрированным состоянием.
4. IBC-канал перенаправляется на новый шард.
5. Старый шард переходит в режим read-only и постепенно останавливается.

**Инструменты:** Cosmos SDK предоставляет `store/v2` migration framework. Для ручной миграции — `genesis.json migrate`. Для миграции данных между версиями кодека — `AltValueCodec` (ленивая миграция).

**Что происходит с транзакциями:**
- Во время миграции шард работает в read-only.
- Новые транзакции буферизуются в Control Chain.
- После завершения миграции буфер разгружается в новый шард.

**Кто платит:** протокол. Стоимость миграции вычитается из резервного пула.

**Длительность:** 1–6 часов в зависимости от размера состояния.

---

### 6. Upgrade mechanism

**Как работает:**
- Предложение в governance с `MsgSoftwareUpgrade`, указывающее имя upgrade и целевую высоту.
- Валидаторы голосуют.
- Если предложение проходит — цепь останавливается на заданной высоте.
- `cosmovisor` автоматически заменяет бинарник и перезапускает узел.

**Кто инициирует:** любой оператор с достаточным депозитом.

**Как голосуют:** стандартное governance-голосование (quorum 33%, порог 50%+1).

**Откат:** если upgrade неудачен — emergency upgrade через `--upgrade-height` с откатом до предыдущей версии.

**Совместимость версий:** `x/upgrade` обеспечивает `BeginBlocker` hook, который предотвращает продолжение state machine до достижения высоты upgrade.

---

### 7. Fraud proofs / validity proofs

**Выбор:** Optimistic rollup с fraud proofs для мелких сумм; validity proofs для крупных.

**Optimistic:**
- Период оспаривания: 1 час для мелких, 24 часа для крупных.
- Кто может подать: любой с Merkle-доказательством.
- Награда: 10% от slashed.
- Штраф за ложный fraud proof: 10% депозита заявителя.

**Validity:**
- ZK-SNARK для кросс-шардовых транзакций > 100 000 P2F.
- Дорого, но даёт мгновенную финальность.

**Что если fraud proof ошибочный:** заявитель теряет депозит, транзакция остаётся валидной.

---

### 8. Light client

**Как работает:**
- Лёгкий клиент синхронизирует только блок-заголовки.
- Проверяет Merkle proofs для состояния и транзакций.
- Не требует полной синхронизации.

**Мобильный:**
- Go light client библиотека (Cosmos SDK `light` package).
- Проверка блок-заголовков, Merkle proof, консенсусных подписей.
- Solo machine light client — для мобильных устройств.

**Как проверяет чекпоинты:**
- Light client отслеживает trusted validator set.
- Проверяет каждый block commit с pre-commit подписями.
- Merkle proof для состояния.

**Кросс-шардовые транзакции:** через IBC light client для каждого шарда.

---

### 9. Cross-shard MEV

**Проблема:** IBC relayer может видеть пакеты и извлекать MEV.

**Защита:**
- **Batch auctions:** relayer группирует пакеты, а не пересылает по одному.
- **Private routing:** пакеты идут через приватный канал.
- **Parallel nonces:** IBC relayer может использовать разные nonce series для параллельных транзакций.
- **Cross-chain proposerless block building:** рандомизация порядка пакетов.

**Рекомендация:** batch auctions + parallel nonces на MVP.

---

### 10. Reputation system

**Как растёт:**
- +10 за эпоху без нарушений.
- +50 за выигранный спор.
- +100 за успешный fraud proof.

**Как падает:**
- -100 за доказанное нарушение.
- -1000 за критическое нарушение.
- -50 за пропуск эпохи.

**Влияние на выбор комитета:** `reputation_factor = 1 + reputation / 1000`.

**Влияние на voting power:** `power = reputation^0.5 * uptime_factor * log(1 + service_score)`.

**Защита от накрутки:** репутация не покупается, не передаётся, проверяется через `x/evidence`.

### 11. Oracle design

**Кто держит:** мультисиг 5 из 7 независимых узлов.

**Консенсус:** 66% подписей для аттестации.

**Как получает данные от Google:** Google Cloud Attestation API. Oracle-узлы независимо запрашивают и проверяют подпись Google.

**Защита от компрометации:** мультисиг, ротация узлов каждые 6 месяцев, аудит, публикация доказательств.

**Альтернативы:** Tellor Layer (L1 на Cosmos SDK для субъективных данных), Band Protocol (100+ валидаторов).

### 12. VRF details

**Схема:** ECVRF на Ed25519.

**Кто держит:** VRF Coordinator (мультисиг 5 из 7).

**Как публикует seed:** seed публикуется до выбора, результат верифицируем.

**Верификация:** ECVRF proof проверяется любым участником.

**Если Coordinator скомпрометирован:** emergency break-glass, пересоздание координатора.

### 13. PoP details

**Основной провайдер:** Worldcoin (World ID).

**Резервный:** Gitcoin Passport.

**Ротация:** каждые 12 месяцев.

**Защита от купленных личностей:** минимальная стоимость PoP + KYC для крупных операторов.

**Апелляция:** через DAO, 7 дней.

---

### 14. MPC details

**Для Ed25519:** FROST (RFC 9591).

**Для ECDSA:** GG20.

**Порог:** 2 из 3 (юзер + 1 VPS) или 3 из 5 (юзер + 2 VPS).

**Ротация долей:** каждые 90 дней.

**Recovery:** через 3 VPS, задержка 60 минут, отмена доступна.

**Потеря доли:** восстановление из backup-шейра, хранящегося у другого VPS.

---

### 15. Multi-sig с другими блокчейнами

**Как P2F участвует:** через threshold signing (FROST/GG20) для Ethereum, Bitcoin, Solana.

**Хранение ключей:** доли у разных VPS, полный ключ никогда не собирается.

**Лимиты и whitelist:** в смарт-контракте на EVM L2, валидаторы берут оттуда.

**Кто платит за газ:** пользователь. P2F не субсидирует.

**Если другая цепочка изменит формат:** обновление адаптера через governance.

### 2. Fee Market v0.1

**Модель:** EIP-1559-like с динамическим base fee.

**Формула base fee:**
```
base_fee_next = base_fee * (1 + (gas_used - target_gas) / target_gas * 0.125)

target_gas = max_gas / 2
max_gas = 10 000 000 (на блок)
```

**Правила:**
- Base fee сжигается на 100%.
- Priority fee идёт валидаторам.
- Если gas_used < target — base fee снижается.
- Если gas_used > target — base fee растёт.
- Максимум изменения за блок: ±12.5%.

**Priority fee:**
- Пользователь сам выбирает.
- Типично: 0.001–0.01 P2F.
- Идёт валидаторам и операторам.

**Распределение комиссий:**

| Компонент | Доля | Кому |
|---|---|---|
| Base fee | 100% | Сжигается |
| Priority fee | 70% | Валидаторы шарда |
| Priority fee | 20% | Операторы (по PFP) |
| Priority fee | 5% | Резервный пул |
| Priority fee | 5% | Фонд развития |

**Защита от gas wars:**
- Base fee растёт автоматически при перегрузке.
- Max gas на блок ограничивает spam.
- Мемпул приоритизирует по priority fee.
- Emergency: при gas_used > 90% max_gas — только base fee, priority fee отключается.

**Cross-shard комиссии:**
- Пользователь платит на исходном шарде.
- Целевой шард получает 20% от priority fee.
- IBC relayer получает 10% от priority fee.

### 3. PFP Supply & Conversion v0.1

**Supply PFP:**

- **Ограничен:** 10 000 000 000 PFP (10 млрд).
- **Эмиссия:** линейно убывающая. 
  - Сезон 1: 500 000 000 PFP.
  - Сезон 2: 400 000 000.
  - Сезон 3: 300 000 000.
  - Сезон 4+: 200 000 000.
- **Максимум:** 10 млрд за 10 лет.

**Почему ограничен:** если PFP бесконечны, конвертация в P2F обесценит P2F.

**Инфляция PFP:** нет. Только фиксированная эмиссия.

**Конвертация PFP → P2F:**

**Модель:** динамический курс, governance определяет раз в сезон.

```
conversion_rate = P2F_pool_for_conversion / total_PFP_emitted

P2F_pool_for_conversion = 100 000 000 P2F в год (из 40% community)
```

**Пример:**
- Сезон 1: 500M PFP, 25M P2F → 1 PFP = 0.05 P2F.
- Сезон 2: 400M PFP, 25M P2F → 1 PFP = 0.0625 P2F.
- Курс может меняться только через governance.

**Механика конвертации:**
- Пользователь конвертирует PFP в P2F в любой момент.
- PFP сжигаются.
- P2F отправляются на кошелёк.
- Курс фиксируется на момент конвертации.
- Курс пересчитывается раз в сезон.

**Защита от обесценивания:**
- PFP ограничены (10 млрд).
- P2F-пул ограничен (25M в год).
- Курс только через governance.
- Ранние участники получают больше.

**Что если PFP накопились за год:**
- Курс пересчитывается.
- Ранние получают по курсу на момент конвертации.
- Нет очереди — все конвертируют по текущему курсу.

### 9. Governance Attack Resistance v0.1

**Возможные атаки:**

| Атака | Защита |
|---|---|
| Накрутка репутации | Проверка через `x/evidence`, PoP |
| Сговор 3 операторов | Quorum 33%, порог 50%+1, veto |
| Покупка голосов | Репутация не покупается |
| Sybil | PoP, депозит, лимиты |
| Flash loan attack | Timelock 48h |
| Governance takeover | Break-glass 5/7 |

**Veto:**
- 33% voting power могут наложить veto.
- Veto отменяет предложение.
- Veto не даёт награды.

**Emergency governance:**
- Только для критических ситуаций.
- Break-glass 5/7.
- Не может переводить средства.
- Публичный журнал.

**Защита от захвата:**
- Voting power = `reputation^0.5 * uptime * log(service)`.
- Логарифм снижает доминирование крупных.
- Квадратный корень анти-плаутократия.
- Максимум 5% voting power на одного оператора.

**Что если 3 крупных сговорятся:**
- Quorum 33% — нужно больше.
- Veto 33% — можно заблокировать.
- Break-glass 5/7 — можно остановить.
- Community может форкнуть.

### 10. DA Cost Model v0.1

**Кто платит за DA:**
- Протокол платит Celestia/Avail.
- Стоимость вычитается из комиссий.

**Сколько стоит:**
- Celestia: ~$0.01 за KB.
- Avail: ~$0.005 за KB.
- 1 блок = ~1 MB.
- 100 шардов × 1 MB × 1440 блоков/день = 144 GB/день.
- Стоимость: ~$720–$1440/день.
- В год: ~$260k–$525k.

**Как влияет на комиссии:**
- 5% от priority fee идёт в DA-пул.
- Если DA-пул < стоимости — комиссии растут.
- Если DA-пул > стоимости — излишек в резерв.

**Что если DA-провайдер поднимет цены:**
- Протокол переключается на альтернативного провайдера.
- Governance решает.
- Emergency: временное снижение DA-частоты.

**Альтернативы:**
- Собственный DA-слой (Phase 7).
- EigenDA (более дешёвый).
- Avail (дешевле Celestia).

**Стратегия:**
- Мульти-DA: Celestia + Avail.
- Автоматический выбор дешёвого.
- Резерв на 6 месяцев.

## ⚖️ РАЗРЕШЕНИЕ ПРОТИВОРЕЧИЙ

### 1. up2f denom

**Решение:** `up2f` = 10^-6 P2F. Стандартная деноминация Cosmos.

- 1 P2F = 1 000 000 up2f.
- Все расчёты внутри — в up2f.
- Отображение — в P2F.

### 2. Whitelist vs Permissionless

**Решение:** чёткая граница по фазам.

| Фаза | Срок | Режим |
|---|---|---|
| Bootstrap | 0–30 дней | Foundation only |
| Phase 1 | 1–6 месяцев | Whitelist 10–20 |
| Phase 2 | 6–12 месяцев | Whitelist 50 |
| Phase 3 | 12–24 месяца | Whitelist 100 |
| Phase 4+ | 24+ месяцев | Permissionless |

### 3. PFP Conversion vs P2F Supply

**Решение:** 
- PFP ограничены (10 млрд).
- P2F-пул для конвертации: 25M в год из 40% community.
- Курс динамический, пересчёт раз в сезон.
- Ранние получают больше.
- Нет обесценивания, потому что supply PFP ограничен.

### 4. MPC Phase 4 vs B2C Phase 1

**Решение:** 
- Phase 1: B2C с обычными ключами (Ed25519).
- Phase 4: переход на MPC.
- До Phase 4 — B2C работает, но без MPC-фичи.
- Это компромисс: быстрее запуск, но меньше фич.

### 5. 100 шардов vs 1M TPS

**Решение:**
- Цель: 1M TPS.
- 100 шардов × 10k TPS = 1M TPS.
- Максимум шардов: не ограничен.
- Если нужно 200 шардов — будут 200.
- 100 — это **расчётный оптимум** для 1M TPS.

### 6. Инфляция vs Награды

**Решение:**
- Инфляция 2% в год: 20M P2F.
- Распределение:
  - 60% валидаторам (12M).
  - 20% операторам (4M).
  - 10% DA-пул (2M).
  - 10% резерв (2M).
- Комиссии идут дополнительно.
- PFP конвертируются из community-пула.
