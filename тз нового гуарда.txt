# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

# Smart Wallet Security System v6.2

## 0. ЦЕЛЬ

Разработать следующую ревизию системы Smart Wallet + Security Guard.

Система должна защищать средства пользователя от:

* malicious smart contracts;
* unlimited `approve`;
* unlimited Permit2 approvals;
* malicious `permit`;
* повторного использования ранее выданного allowance;
* подмены target contract;
* превышения лимитов;
* drain дешевых/неликвидных токенов;
* эксплуатации токенов без надежной цены;
* компрометации frontend;
* компрометации отдельного DeFi-протокола;
* повторного использования разрешения после его окончания;
* ошибочного или злонамеренного увеличения лимитов;
* migration-ошибок;
* reentrancy;
* обхода Guard через прямые вызовы Wallet.

Система должна быть:

* non-custodial;
* on-chain enforceable;
* без backend как security authority;
* без external API внутри transaction path;
* без simulation внутри transaction path;
* без DEX-specific adapters;
* без необходимости знать ABI каждого DeFi-протокола;
* максимально gas-efficient;
* modular;
* пригодной для независимого аудита.

---

# 1. ГЛАВНЫЙ ПРИНЦИП

Guard НЕ должен пытаться понимать логику каждого DeFi-протокола.

Нельзя строить архитектуру:

```text
UniswapAdapter
CurveAdapter
AaveAdapter
GMXAdapter
BalancerAdapter
PendleAdapter
...
```

Количество протоколов потенциально неограниченно.

Вместо этого используется универсальная модель:

```text
Smart Wallet
      │
      ▼
SmartWalletGuard
      │
      ├── PolicyRegistry
      ├── OwnerRegistry
      ├── SubscriptionRegistry
      └── MigrationHub
      │
      ▼
Target Contract
```

Guard контролирует:

1. кто инициировал операцию;
2. какой target;
3. разрешен ли target;
4. какой лимит установлен для target;
5. какой lifetime budget уже потрачен;
6. какие токены участвуют;
7. какой risk category у токена;
8. сколько токена разрешено использовать;
9. какой процент текущего баланса может быть использован;
10. deadline;
11. signatures;
12. временный allowance;
13. native value;
14. blacklist;
15. migration state;
16. subscription permissions.

Guard НЕ обязан понимать внутреннюю бизнес-логику target contract.

---

# 2. КЛЮЧЕВОЕ ОГРАНИЧЕНИЕ

В версии v6.2 НЕ использовать transaction simulation.

Нельзя:

```text
eth_call
Tenderly
BlockSec
GoPlus Simulation
backend simulation
RPC simulation
```

внутри исполнения транзакции.

Причина:

* дополнительная задержка;
* зависимость от RPC;
* дополнительная инфраструктура;
* дополнительные точки отказа;
* непредсказуемый UX;
* security logic становится зависимой от внешнего сервиса.

Transaction path должен работать только на:

* calldata;
* on-chain policy;
* on-chain token configuration;
* current balances;
* signatures;
* local state;
* blockchain state.

---

# 3. ВАЖНАЯ ОГОВОРКА ПО GENERIC EXECUTION

Без simulation Guard не может доказать, что внутренний вызов протокола фактически потратил именно заявленное количество каждого токена.

Поэтому безопасность должна обеспечиваться не попыткой "понять calldata", а временными allowance.

Пример:

Пользователь хочет обменять:

```text
100 USDC
```

через:

```text
Target = Uniswap Router
```

Guard:

1. проверяет policy;
2. проверяет USDC risk policy;
3. проверяет lifetime budget;
4. проверяет max balance share;
5. проверяет signatures;
6. SmartWallet временно дает target allowance ровно:

```text
100 USDC
```

7. SmartWallet вызывает target;
8. target может использовать максимум предоставленных 100 USDC;
9. после вызова SmartWallet отзывает allowance;
10. Guard фиксирует фактическую/разрешенную операцию согласно модели accounting.

Нельзя оставлять:

```text
approve(target, type(uint256).max)
```

после операции.

---

# 4. КАТЕГОРИИ ТОКЕНОВ

Система использует три категории.

```solidity
enum TokenRisk {
    GREEN,
    YELLOW,
    RED
}
```

## GREEN

Токен имеет надежную on-chain цену.

Для GREEN используется:

```text
USD lifetime limit
+
max % current token balance
```

Например:

```text
USDC
GREEN

Contract limit:
$1,000

Current balance:
$2,000

Max balance share:
20%
```

Максимальная операция:

```text
min(
    remaining USD budget,
    20% current balance
)
```

---

# 5. YELLOW

Токен имеет:

* низкую ликвидность;
* нестабильную цену;
* недостаточно надежный price source;
* ограниченную рыночную историю;
* потенциально manipulable price.

Для YELLOW нельзя полагаться только на USD.

Используется:

```text
absolute token amount lifetime limit
+
max % current balance
```

Например:

```text
TOKEN X
YELLOW

maxAmount:
10,000 TOKEN

maxBalanceShare:
20%
```

---

# 6. RED

RED:

* нет надежной цены;
* неизвестный токен;
* новый токен;
* отсутствует валидный price configuration;
* невозможно надежно определить USD value.

Используется:

```text
absolute token amount lifetime limit
+
max % current balance
```

RED должен быть максимально строгим.

---

# 7. UNKNOWN TOKEN

Если токен отсутствует в TokenRiskRegistry:

```text
UNKNOWN => RED
```

Никогда:

```text
UNKNOWN => GREEN
```

Нельзя автоматически доверять новому токену.

---

# 8. ПОЛЬЗОВАТЕЛЬ НЕ ВЫБИРАЕТ RISK CATEGORY

Пользователь НЕ должен вручную выбирать:

```text
GREEN
YELLOW
RED
```

Категория определяется системой.

Например:

```text
USDC -> GREEN
WETH -> GREEN
ABC -> YELLOW
XYZ -> RED
UNKNOWN -> RED
```

Изменение категории должно происходить governance-путем.

---

# 9. PRICE CONFIGURATION

Для GREEN используется on-chain configuration.

Пример:

```solidity
struct TokenPriceConfig {
    uint256 price;
    uint8 decimals;
    uint64 updatedAt;
    uint64 maxAge;
    bool enabled;
}
```

Обязательно проверять:

```text
enabled == true
```

и:

```text
block.timestamp <= updatedAt + maxAge
```

Если цена устарела:

```text
GREEN
```

не должна продолжать автоматически считаться надежной.

В таком случае токен переводится в strict behavior:

```text
GREEN price stale
        ↓
YELLOW/RED-like enforcement
```

Точная реализация может хранить категорию отдельно, но expired price НЕ должен использоваться как валидная цена.

---

# 10. TOKEN POLICY

Создать отдельный TokenRiskRegistry.

Пример:

```solidity
struct TokenRiskConfig {
    TokenRisk risk;
    bool enabled;

    uint256 price;
    uint8 priceDecimals;

    uint64 priceUpdatedAt;
    uint64 priceMaxAge;
}
```

Не помещать тяжелую token-risk логику в Guard.

Guard должен только обращаться к registry.

---

# 11. CONTRACT WHITELIST

Whitelist должен быть:

```text
contract-level
```

а не:

```text
contract + token
```

То есть пользователь добавляет:

```text
0xUniswapRouter
```

а не:

```text
0xUniswapRouter + USDC
0xUniswapRouter + ETH
0xUniswapRouter + WETH
...
```

Это существенно упрощает UX.

---

# 12. CONTRACT POLICY

Использовать:

```solidity
struct ContractPolicy {
    bool enabled;

    uint256 usdLimit;
    uint256 usdSpent;

    uint256 maxTokenShareBps;

    uint64 deadline;

    bool blocked;
}
```

Но структуру можно изменить для gas/storage optimization.

---

# 13. CONTRACT POLICY SEMANTICS

Пример:

```text
Target:
Uniswap Router

Limit:
$1,000

Spent:
$350

Remaining:
$650

Max token share:
20%

Deadline:
30 days
```

Пока:

```text
usdSpent < usdLimit
```

операции могут проходить без дополнительного elevation, если остальные условия соблюдены.

---

# 14. LIMIT = LIFETIME BUDGET

Лимиты должны быть cumulative.

Нельзя:

```text
maxAmount = 100 USDC
```

понимать как:

```text
100 USDC per transaction
```

Это должно означать:

```text
100 USDC lifetime budget
```

Например:

```text
maxAmount = 100

transaction #1 = 30
spent = 30

transaction #2 = 20
spent = 50

transaction #3 = 50
spent = 100

remaining = 0
```

Следующая операция:

```text
REVERT
```

если пользователь не изменил policy.

---

# 15. TOKEN AMOUNT POLICY

Для YELLOW/RED:

```solidity
struct TokenAmountPolicy {
    uint256 maxAmount;
    uint256 amountSpent;
    uint256 maxBalanceShareBps;
}
```

Проверка:

```text
requestedAmount <= maxAmount - amountSpent
```

и:

```text
requestedAmount <= currentBalance * maxBalanceShareBps / 10_000
```

Обе проверки обязательны.

---

# 16. ПОЧЕМУ НУЖНЫ ДВА ЛИМИТА

Нельзя использовать только:

```text
20% balance
```

Потому что:

```text
1000
→ 800
→ 640
→ 512
→ 409
→ ...
```

При повторных операциях можно постепенно вывести почти весь баланс.

Поэтому:

```text
Lifetime amount
+
Per-transaction balance share
```

обязательны одновременно.

---

# 17. GREEN ACCOUNTING

Для GREEN:

```text
USD lifetime budget
```

и:

```text
maxBalanceShareBps
```

Пример:

```text
USDC price = $1

USD limit = $1,000
USD spent = $300

Remaining = $700
```

Если баланс:

```text
$5,000
```

и:

```text
maxBalanceShare = 20%
```

то transaction maximum:

```text
$1,000
```

Но lifetime remaining:

```text
$700
```

Следовательно:

```text
max allowed = $700
```

---

# 18. YELLOW/RED ACCOUNTING

Для YELLOW/RED не использовать USD как единственный security boundary.

Например:

```text
TOKEN balance = 1,000,000
maxBalanceShare = 10%
maxAmount = 100,000
amountSpent = 20,000
```

Remaining lifetime:

```text
80,000
```

Current per-tx max:

```text
100,000
```

Следовательно:

```text
max allowed = 80,000
```

---

# 19. APPROVE НЕ ЯВЛЯЕТСЯ SPEND

Это КРИТИЧЕСКОЕ правило.

Если пользователь делает:

```solidity
approve(target, 100 USDC)
```

это НЕ означает:

```text
spent = 100
```

Allowance ≠ actual spend.

Поэтому:

```text
approve()
```

не должен увеличивать:

```text
usdSpent
amountSpent
```

---

# 20. APPROVE POLICY

Unlimited approve:

```solidity
approve(target, type(uint256).max)
```

должен быть запрещен.

Также запрещать:

```text
uint256 max
Permit unlimited
Permit2 unlimited
infinite expiration
```

если это не специально разрешенный системный механизм.

Для пользовательского target:

```text
amount == 0
```

может означать revoke.

---

# 21. EXACT APPROVE

Допустимо:

```text
approve(target, 15 USDC)
```

если:

```text
15 <= permitted amount
```

Например:

```text
Contract lifetime limit:
$1000

Spent:
$350

Remaining:
$650
```

Пользователь может дать:

```text
approve 15 USDC
```

но это НЕ увеличивает spent.

---

# 22. PROBLEM WITH PERSISTENT APPROVAL

Если:

```text
approve(target, 1000 USDC)
```

остается после операции, Guard уже не контролирует последующие `transferFrom`.

Поэтому generic execution должен использовать:

```text
temporary allowance
```

а не permanent allowance.

---

# 23. TEMPORARY ALLOWANCE MODEL

Рекомендуемый flow:

```text
Guard
 ↓
validate policy
 ↓
validate signatures
 ↓
SmartWallet.approveTokenByGuard(
    token,
    target,
    amount
)
 ↓
SmartWallet.callTarget(
    target,
    value,
    calldata
)
 ↓
SmartWallet.revokeTokenAllowanceByGuard(
    token,
    target
)
```

Важно:

`approveTokenByGuard()` должен исполняться SmartWallet.

Не:

```text
Guard -> token.approve()
```

Потому что тогда:

```text
msg.sender == Guard
```

и allowance будет:

```text
Guard -> target
```

а не:

```text
SmartWallet -> target
```

---

# 24. SMART WALLET APPROVAL PRIMITIVE

Добавить:

```solidity
function approveTokenByGuard(
    address token,
    address spender,
    uint256 amount
) external onlyGuard;
```

Требования:

* `onlyGuard`;
* token != zero;
* spender != zero;
* spender != address(this);
* no arbitrary caller;
* no delegatecall;
* forceApprove для USDT-like tokens;
* amount должен быть конечным;
* unlimited amount запрещен на уровне Wallet primitive, если это не системная функция;
* event.

---

# 25. REVOKE PRIMITIVE

Добавить:

```solidity
function revokeTokenAllowanceByGuard(
    address token,
    address spender
) external onlyGuard;
```

Делает:

```solidity
forceApprove(spender, 0)
```

Wallet должен использовать этот primitive после generic call.

---

# 26. ATOMICITY

Операция:

```text
temporary approve
+
target call
+
revoke
```

должна находиться в одной транзакции.

Если target call revert:

```text
вся транзакция revert
```

и approval тоже откатывается.

Если call успешен:

```text
revoke
```

должен выполняться до завершения.

---

# 27. REENTRANCY

Generic execution должен быть:

```solidity
nonReentrant
```

или использовать эквивалентную безопасную архитектуру.

Особенно опасны:

```text
Wallet -> Target
Target -> Token
Token -> Target
Target -> Wallet
```

Нельзя разрешать target самостоятельно повторно вызывать Wallet primitives.

Wallet primitives должны быть:

```text
onlyGuard
```

---

# 28. НИКАКОГО DELEGATECALL

Wallet/Guard не должен предоставлять пользователю generic:

```solidity
delegatecall(target, data)
```

Delegatecall принципиально запрещен.

Разрешен только:

```text
CALL
```

в заранее разрешенный target.

---

# 29. GENERIC EXECUTE

Создать:

```solidity
executeContract(
    address target,
    uint256 value,
    bytes calldata data,
    TokenSpend[] calldata spends,
    OperationAuth calldata auth
)
```

Точная сигнатура может быть изменена ради gas optimization.

---

# 30. TokenSpend

Например:

```solidity
struct TokenSpend {
    address token;
    uint256 amount;
}
```

Операция явно заявляет:

```text
USDC: 100
WETH: 0.1
```

Guard проверяет policy для каждого token.

---

# 31. TARGET

Target должен быть:

```text
approved
AND
not blocked
AND
not blacklisted
AND
policy enabled
AND
deadline valid
```

Если target неизвестен:

```text
REVERT
```

---

# 32. TARGET POLICY = 0

Если пользователь выставил:

```text
limit = 0
```

это НЕ означает:

```text
contract blocked
```

Это означает:

```text
каждая spend operation требует elevation
```

То есть:

```text
2/3 Hot
+
Special Local Authorization
```

---

# 33. SPECIAL LOCAL AUTHORIZATION

Нужен отдельный механизм повышенной авторизации.

Смысл:

```text
2/3 Hot
+
special local key
```

Special key:

* хранится локально;
* защищается device password;
* никогда не отправляется backend;
* не хранится plaintext on-chain;
* используется для high-risk operation authorization.

---

# 34. ПАРОЛЬ

Пароль НЕ должен быть on-chain security secret.

Правильная модель:

```text
device password
       ↓
local key unlock
       ↓
special signature
       ↓
Guard
```

Guard получает:

```text
signature
```

но не пароль.

---

# 35. NORMAL OPERATION

Обычная операция:

```text
2/3 Hot
```

если она находится внутри policy.

Например:

```text
Contract:
Uniswap

Limit:
$1000

Spent:
$300

Operation:
$100

Risk:
GREEN

Balance share:
10%
```

Если все policy checks проходят:

```text
2/3 Hot
```

достаточно.

---

# 36. HIGH-RISK OPERATION

Если policy не позволяет автоматическое выполнение:

```text
2/3 Hot
+
Special Key
```

Например:

```text
limit = 0
```

Любая операция требует:

```text
2/3 Hot + Special Key
```

---

# 37. LIMIT INCREASE

Если пользователь хочет увеличить:

```text
$1000 → $5000
```

это отдельная critical policy operation.

Она не должна происходить просто потому, что frontend отправил:

```text
newLimit = 5000
```

Требуются соответствующие signatures согласно governance policy.

---

# 38. NEAR LIMIT WARNING

Frontend должен показывать:

```text
Contract limit almost reached
```

Например:

```text
Spent:
$920

Limit:
$1000

Remaining:
$80
```

UI:

```text
Increase limit
Block contract
Set limit = 0
```

Это UX, не security authority.

On-chain Guard всё равно проверяет limit самостоятельно.

---

# 39. BLOCK CONTRACT

Если:

```text
blocked = true
```

любая обычная operation:

```text
REVERT
```

Даже если:

```text
usdSpent < usdLimit
```

и:

```text
deadline valid
```

---

# 40. CONTRACT DEADLINE

Policy должна иметь:

```solidity
uint64 deadline;
```

Если:

```text
block.timestamp > deadline
```

операция запрещается.

Deadline не должен быть:

```text
0 = forever
```

если policy этого явно не предусматривает.

Для security-sensitive whitelist желательно иметь finite deadline.

---

# 41. BLACKLIST

Blacklists должны иметь priority выше whitelist.

Порядок:

```text
BLACKLIST
   ↓
REVERT
```

даже если:

```text
WHITELIST = true
```

---

# 42. TOKEN BLACKLIST

Token blacklist должен блокировать spend.

Например:

```text
Token:
ABC

blocked = true
```

Любая generic operation:

```text
ABC
```

revert.

---

# 43. CONTRACT BLACKLIST

Если target:

```text
blacklisted
```

любая операция через него запрещена.

---

# 44. NATIVE TOKEN

Native asset:

```solidity
address(0)
```

или существующая:

```solidity
NATIVE
```

константа.

Native transfers должны использовать отдельный narrow primitive:

```solidity
sendNativeByGuard()
```

Generic contract call с native value должен:

1. пройти target policy;
2. иметь explicit native value limit;
3. пройти signatures;
4. не иметь возможности превысить configured value budget.

---

# 45. NATIVE VALUE

Если generic target call:

```text
value > 0
```

то:

```text
value
```

должен быть явно подписан.

Нельзя брать:

```text
msg.value
```

как неограниченное значение.

---

# 46. PERMIT2

Permit2 остается частью security architecture.

Permit2 используется для контролируемых token operations.

Но:

```text
Permit2 unlimited approval
```

для пользовательских target contracts запрещается.

---

# 47. PERMIT2 EXPIRATION

Для Permit2:

```text
expiration == 0
```

для пользовательских allowance должен считаться invalid.

Использовать:

```text
finite expiration
```

и:

```text
expiration >= block.timestamp
```

---

# 48. PERMIT

Любой permit, который создает unlimited allowance:

```text
REVERT
```

если он не относится к специально разрешенному internal/system flow.

---

# 49. APPROVAL VS SPEND

Обязательно разделить:

```text
approved allowance
```

и:

```text
actual budget spent
```

Не делать:

```solidity
usdSpent += approveAmount;
```

Никогда.

---

# 50. ACCOUNTING

Для GREEN:

```text
usdSpent
```

Для YELLOW/RED:

```text
amountSpent[token]
```

Для contract-level global budget:

```text
contract.usdSpent
```

может учитывать только операции, которые действительно расходуют budget.

---

# 51. ВАЖНЫЙ ВОПРОС ACTUAL SPEND

Без simulation Guard не должен притворяться, что он способен точно определить все внутренние token movements.

Поэтому архитектура должна гарантировать:

```text
maximum possible spend <= explicitly authorized allowance
```

То есть безопасность достигается через:

```text
temporary allowance
```

а не через попытку распарсить каждый внутренний вызов.

---

# 52. ОГРАНИЧЕНИЕ GENERIC CALL

Generic call не должен предоставлять target постоянный доступ к Wallet.

После операции:

```text
allowance = 0
```

для каждого token.

---

# 53. ЕСЛИ TARGET НЕ ИСПОЛЬЗОВАЛ ALLOWANCE

Например:

```text
approve = 100
actual spend = 70
```

после call:

```text
allowance = 0
```

Оставшиеся:

```text
30
```

не остаются доступными target.

---

# 54. ACCOUNTING В ЭТОМ СЛУЧАЕ

Есть два варианта.

Рекомендуемый для первой версии:

```text
budget accounting based on authorized spend
```

То есть если пользователь авторизовал:

```text
100
```

из lifetime budget резервируется:

```text
100
```

даже если target использовал 70.

Причина:

* deterministic;
* не требуется post-state analysis;
* не зависит от нестандартных токенов;
* невозможно получить accounting bypass.

Unused amount не остается allowance.

В будущем можно добавить более сложный actual-spend accounting, но не в v6.2.

---

# 55. RESERVATION MODEL

Для операции:

```text
requested = 100
```

до вызова:

```text
amountSpent += 100
```

Если операция revert:

```text
transaction rollback
```

и:

```text
amountSpent
```

также откатывается.

Это автоматически дает atomic accounting.

---

# 56. GREEN RESERVATION

Для GREEN:

```text
usdSpent += requestedUSD
```

до target call.

Если target revert:

```text
rollback
```

Если success:

```text
budget consumed
```

---

# 57. YELLOW/RED RESERVATION

Для YELLOW/RED:

```text
amountSpent[token] += requestedAmount
```

до target call.

---

# 58. TOKEN BALANCE SHARE

Проверять balance ДО выдачи allowance:

```solidity
balance = IERC20(token).balanceOf(wallet)
```

Проверка:

```text
amount <= balance * maxBalanceShareBps / 10_000
```

Не использовать balance Guard.

Использовать:

```text
SmartWallet balance
```

---

# 59. ZERO BALANCE

Если:

```text
balance == 0
```

любая token spend:

```text
REVERT
```

---

# 60. MAX BPS

```solidity
10_000 = 100%
```

Нельзя позволять:

```text
maxBalanceShareBps > 10_000
```

---

# 61. 100% BALANCE

Даже:

```text
100%
```

должно использоваться только если policy governance это разрешает.

Для RED рекомендуется не позволять default 100%.

# 64. CHECKS-EFFECTS-INTERACTIONS

Стараться соблюдать:

```text

 ↓

 ↓
```

# 65. EVENTS

Добавить события минимум:

```solidity
event ContractPolicyUpdated(...);

event ContractBlocked(...);

event ContractUnblocked(...);

event TokenRiskUpdated(...);

event TokenPriceUpdated(...);

event ContractExecutionStarted(...);

event ContractExecutionCompleted(...);

event TokenAllowanceGranted(...);

event TokenAllowanceRevoked(...);

event BudgetReserved(...);

event SpecialAuthorizationUsed(...);
```

События не должны содержать секреты.

---

# 66. NONCE

Каждая подписанная операция должна иметь nonce.

Например:

```solidity
uint256 nonce;
```

или:

```solidity
mapping(bytes32 => uint256) nonce;
```

Нельзя повторно использовать одну и ту же authorization.

---

# 67. EIP-712

Использовать EIP-712 для structured signing.

Подписываемые данные должны включать минимум:

```text
wallet
guard
target
value
calldataHash
token spend list hash
nonce
deadline
policy version / policy hash
```

Если требуется special key:

```text
special authorization
```

также должна быть domain-separated.

---

# 68. CALldata HASH

Нельзя подписывать только:

```text
target
```

Пользователь должен авторизовать конкретный calldata:

```solidity
keccak256(data)
```

Иначе frontend может заменить:

```text
swap(...)
```

на:

```text
maliciousFunction(...)
```

при том же target.

---

# 69. TARGET + CALLDATA

Signature должна связывать:

```text
target
+
value
+
calldata
+
token spends
```

---

# 70. TOKEN SPEND HASH

Список:

```text
USDC 100
WETH 0.1
```

должен быть частью signed operation.

Нельзя разрешить frontend самостоятельно изменить:

```text
100 USDC
```

на:

```text
10,000 USDC
```

после подписи.

---

# 71. OWNER MODEL

Сохранить текущую модель:

```text
5 owners
```

из которых:

```text
3 Hot
2 Cold
```

---

# 72. NORMAL OPERATION

Normal:

```text
2/3 Hot
```

---

# 73. CRITICAL OPERATION

Critical:

```text
3/5 owners
+
at least 1 Cold
```

---

# 74. EMERGENCY

Emergency Sweep:

```text
2/3 Hot
```

Cold не требуется.

---

# 75. EMERGENCY SWEEP

Emergency Sweep НЕ должен зависеть от:

```text
subscription
whitelist
approved token
contract policy
normal spend limits
```

Он должен оставаться emergency mechanism.

Но обязательно:

```text
paused wallet
+
registered recovery target
+
recipient blacklist check
+
token blacklist check
+
2/3 Hot
```

---

# 76. EMERGENCY RECOVERY

Emergency recovery key остается:

```text
full custody key
```

для соответствующего Wallet.

Это critical security assumption и должно быть явно документировано.

---

# 77. WALLET ISOLATION

Hot Wallet и Cold Wallet остаются отдельными Smart Wallet.

Hot:

```text
operational funds
```

Cold:

```text
high-value reserve
```

Guard должен знать конкретный wallet binding.

---

# 78. NO DIRECT WALLET BYPASS

Ни одна функция Wallet не должна позволять:

```text
EOA -> Wallet -> arbitrary target
```

минуя Guard.

Особенно:

```text
execute
call
approve
transfer
delegatecall
```

---

# 79. WALLET CALL PRIMITIVE

Добавить ограниченный primitive:

```solidity
function executeTarget(
    address target,
    uint256 value,
    bytes calldata data
)
    external
    onlyGuard
    returns (bytes memory);
```

Ограничения:

```text
target != address(0)
```

если это необходимо.

Не разрешать:

```text
delegatecall
```

---

# 80. RETURN DATA

Generic call должен возвращать:

```text
success
returnData
```

Но Guard не должен доверять revert data как security signal.

Solidity предупреждает, что revert data может быть сформировано/подделано вызываемым контрактом и не должно использоваться как источник доверия.

---

# 81. CODE EXISTENCE

Перед вызовом target желательно проверить:

```solidity
target.code.length > 0
```

если target должен быть contract.

EOA как generic target:

```text
REVERT
```

---

# 82. NO ARBITRARY SELF-CALL

Запретить:

```text
target == wallet
```

для generic execution, если только конкретный внутренний system call не разрешен отдельно.

# 83. NO GUARD SELF-CALL

# 100. EIP-170

Текущий Guard находится близко к лимиту runtime bytecode.

НЕ добавлять в Guard:

* сложные libraries;
* дополнительные massive structs;
* огромные loops;
* ABI-heavy helpers;
* лишние validation functions.

```text
PolicyRegistry
OwnerRegistry
SubscriptionRegistry
MigrationModule
TokenRiskRegistry
```

# 188. INVARIANTS

### INVARIANT 4

Lifetime budget никогда не уменьшается сам по себе.

### INVARIANT 5

`spent <= limit`.

### INVARIANT 6

`maxBalanceShareBps <= 10_000`.

### INVARIANT 7

Unknown token никогда не получает GREEN security treatment автоматически.

### INVARIANT 8

Blacklist всегда сильнее whitelist.

### INVARIANT 9

Одна authorization не может быть replayed.

### INVARIANT 10

Target не может вызвать Wallet primitives напрямую.

# 249. ФИНАЛЬНАЯ МОДЕЛЬ

Вся система должна сводиться к следующей простой формуле:

```text
WHO
+
WHERE
+
WHAT
+
HOW MUCH
+
HOW OFTEN
+
HOW RISKY
+
HOW MUCH OF BALANCE
+
UNTIL WHEN
+
WHO SIGNED
```

То есть:

```text
WHO
= owners / signatures

WHERE
= target contract

WHAT
= calldata

HOW MUCH
= token amount / native value

HOW OFTEN
= lifetime budget

HOW RISKY
= GREEN / YELLOW / RED

HOW MUCH OF BALANCE
= maxBalanceShareBps

UNTIL WHEN
= deadline

WHO SIGNED
= EIP-712 authorization
```

А Wallet предоставляет target только:

```text
temporary exact allowance
```

на конкретную операцию.

После операции:

```text
allowance = 0
```

# 250. КЛЮЧЕВАЯ ИДЕЯ V6.2

Guard не должен быть:

> "AI, который понимает, что делает каждый DeFi-контракт."

Guard должен быть:

> **"криптографически и on-chain контролируемым firewall между Smart Wallet и любым внешним smart contract."**

Он не обязан понимать:

```text
swap
lend
borrow
stake
LP
bridge
perp
prediction market
NFT
GameFi
```

Он должен понимать:

```text
кому
что
сколько
на какой срок
с каким risk budget
с каким balance limit
и с какими подписями
```

И именно поэтому архитектура масштабируется на новые протоколы без создания нового adapter для каждого DEX.
